# Feature Design: Add NFS Support to VM

## Summary

Extend the existing Debian VM provisioning contract with NFS client tooling,
safe disabled examples, and local user guidance. Preserve DHCP as the default
and avoid making the image depend on a site-specific NFS service or Internet
access.

## Proposed Approach

1. Add the Debian NFS client package(s) to the VM runtime provisioning path.
2. Keep `configure-dhcp-networkd.sh` as the active default, but make its
   ownership and non-default behavior explicit in comments and documentation.
3. Ship a static `.network` example that is not loaded by `systemd-networkd` by
   default, such as a clearly named example file or commented configuration.
4. Ship an NFS mount example with placeholders and disabled state; do not add a
   real `/etc/fstab` entry or automatic service.
5. Extend the existing cloud-init MOTD and `QUICKSTART.txt` rather than adding
   a second login mechanism.
6. Put complete enough network/NFS diagnostics in the image for air-gapped use,
   while noting that RPC-based discovery is not universal.

## Data Model Or Schema Changes

None. This feature changes VM provisioning and documentation only.

## Interfaces And User Experience

- Default login guidance identifies `systemd-networkd`, DHCP, and the active
  configuration path.
- Network diagnostics include `networkctl`, `ip`, and `resolvectl`.
- NFS diagnostics include `nfsstat`, `mount.nfs`, and, where useful,
  `rpcinfo`/`showmount`.
- The quickstart gives manual mount, test, parse, and unmount examples for
  input and output volumes.
- The quickstart calls NFS optional and identifies local storage and other
  transfer mechanisms as valid alternatives.

## Edge Cases

- Interface names may differ from `en*` on a future image or hypervisor.
- A static example must not be a valid competing `.network` file that wins
  matching before the DHCP file.
- NFSv4-only servers may not answer `showmount` or expose expected RPC services.
- An NFS export may be read-only, so output tests must verify permissions.
- A local NFS server may be reachable in an air-gapped environment while the
  Internet remains unavailable.

## Error Handling

- Provisioning should fail if required runtime packages cannot be installed at
  image-build time.
- Optional discovery commands should report limitations without making the VM
  unusable.
- Mount examples should show explicit failure checks and clean unmounting.
- No first-boot script should retry Internet downloads or silently install
  missing runtime dependencies.

## Risks

- Network filesystem semantics may be unsuitable for an active DuckDB database;
  the feature explicitly keeps the active database local.
- Duplicate or incorrectly named `.network` files could change the DHCP default.
- NFS package contents and discovery tools vary by Debian release and NFS server.
- Testing may be limited by access to a representative local NFS server.

## Alternatives Considered

- **Automatic NFS mount:** rejected because the server/export is deployment
  specific and NFS is optional.
- **NFS server inside the VM:** rejected; the VM is a client for external data
  and output storage.
- **New login application or service:** rejected; the existing MOTD and local
  quickstart already provide the required surface.
- **Static networking as the default:** rejected; DHCP remains portable across
  current hypervisors.

## Open Questions

- Select the primary live hypervisor/NFS server test target.
- Decide whether the static example is generated by provisioning or simply
  shipped as a local reference file.
